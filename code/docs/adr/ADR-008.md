# ADR-008 — Configuration as code with versioned revisions

- **Status:** Accepted
- **Date:** 2026-11-03
- **Author:** Freddy Beltran

## Context
Table/column configuration must be reviewable, reversible and auditable.

## Decision
Configuration lives as YAML in Git (`config/`). Console edits create numbered `config_revision`s in hub Postgres, exportable to YAML; rollback = a new revision equal to an older one.

## Consequences
- Every change has author, reason and diff; audit trail is complete.
- Git and hub may diverge temporarily; export/import tooling reconciles.

## Amendment 2026-11-04 — one source of truth (design review F-18)
- The hub metadata DB is **authoritative**. Every change (console edit, wizard, migration import, YAML import,
  rollback, upgrade) is a `config_revision`; the full tables.yaml document of each connection it touches is stored in
  `config_doc`. The active config of a connection = its newest `config_doc` (`hub/alelt_hub/config_store.py`).
- YAML in Git is **import/export only**: `alelt config export <connection>` (diffable, header names the revision),
  `alelt config import FILE --reason ...` / `POST /api/v1/config/connections/{id}/import` (dry-run diff first).
  `ALELT_TABLES_CONFIG` files are imported once for a connection without revisions (first start / upgrade); later
  differences are reported (`alelt config diff`, metric `alelt_config_file_drift`, alert `AleltConfigFileDrift`), never
  applied silently.
- Console, wizard, importer, loader/worker, snapshots and diagnosis all read the active revision
  (`store.connection_policy`); `pipeline_definition.tables_doc` is a materialized copy written in the same transaction.
- Documents carry `config_version`; older ones are migrated on import (deploy/UPGRADE.md §5).
